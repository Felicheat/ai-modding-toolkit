## ModWorldSubsystem recipe
A `ModWorldSubsystem` Blueprint in NewContent that spawns a mod actor overrides no game asset, so it cannot conflict with
other mods, and NewContent Blueprints keep their references to other NewContent assets.
1. `/<Mod>/Runtime/BP_<Short>Subsystem`, parent `ModWorldSubsystem`, listed in NewPackages.txt.
2. Press **Package Mod** once in the editor: only that generates `Autogenerated_<n>_WorldSubsystemData` (a soft class path
   to the subsystem) into the mod's Content and adds it to OverridePackages.txt. Without it the game never creates the
   subsystem. Copy it into `<repo>` too.
3. `OnInitialized`: `SetTickEnabled(true)` (a ModWorldSubsystem does not tick until enabled).
4. `OnTick`: `Branch(IsValid(<actor variable>))`, False: `SpawnActorFromClass(BP_<Short>Actor)` and set the variable. Keep
   ticking and re-spawn when invalid: a spawn-once-then-stop-ticking graph spawned too early and the actor was gone. One
   subsystem per world (`WorldMap_WP`); the actor lives in `PersistentLevel`.
5. The actor: `AutoReceiveInput = Player0` on the CDO (settable from Python) or `EnableInput`, EnhancedInputAction events
   for its keys, per-tick logic with edge detection (do the work on state changes, not every frame).
6. Get the pawn with `Get Player Pawn`, then `Cast To PC` (the native player class; `BP_Stalker2Character_C` at runtime).

## Rules of thumb
- Only the subsystem data asset (and unavoidable overrides) goes in the override pak; everything else is NewContent.
- Never scan all objects per tick: `ForEachUObject` / `GetAllActorsOfClass` every frame stalls the game thread (a 1.44 s
  stall once read to players as "no control"). Read from owners: pawn components, mesh linked instances, the camera
  manager's modifier list.
- `AddTickPrerequisiteComponent` makes the actor tick before, for example, the player mesh when order matters.
- Keep settings in actor or subsystem variables with defaults, so the main mod needs nothing else; an optional settings
  menu add-on writes them.

## How the game does input
- Enhanced Input. Contexts are `IMC_*` assets; `InputMappingContextPrototypes.cfg` names each context and its priority
  (`IMC_Exploration`: Lowest; `IMC_PlayerCA`, the contextual-action sit: Exclusive, which suppresses every lower context).
  Priorities and which context is active decide which keys exist at all.
- Native input handlers (`*IPU` classes such as `PDAOpenIPU`, `InventoryIPU`, `QuickSlot*IPU`) consume the actions and
  apply the game's own gates; they have no Blueprint surface and no cfg. A key reaching the action does not mean the
  action runs: use a canary row to tell "override not loaded" from "vetoed natively".
- Some input action assets carry action-level triggers (Tap / Hold / Down). `InputTriggerActionBlocker` would be an
  asset-side veto. Check with `scripts/dump_imc.py` (it prints `action_triggers`).
- The on-screen key legend does not list rows a mod adds.

## Player rebinds (Options > Controls)
- Stored by the game, not in Unreal's user settings: `%LOCALAPPDATA%/Stalker2/Saved/CustomizeControls.cfg`, one `struct`
  section per context (`Exploration`, `Aiming`, `Dialogue`, `PlayerContextualAction`, ...), rows with
  `PlayerMappableOption` (the row's mappable name, such as `MoveForward`), `InputActionSID`, `Key`, `OldKey`, `Triggers`.
- A rebind only reaches rows that carry the mappable name: `SettingBehavior = OverrideSettings` + a
  `PlayerMappableKeySettings` with the game's name. Rows built without it stay on their literal keys (AZERTY players then
  cannot use them). Always check with `scripts/dump_imc.py`: `mappable` must read `OverrideSettings/<Name>`.
- The game only writes a context's section when the player applies bindings with that context known, and it applies binds
  to the game-path object only. Do not rely on players re-applying bindings: sync keys at runtime.
- Layouts: Unreal names keys by what they type (the W position reports `Z` on AZERTY); the game does not translate layouts.

## Input techniques
- **Load the game-path context by string** at runtime: `Make Soft Object Path`
  ("/Game/_Stalker_2/data/input/InputMappingContexts/IMC_X.IMC_X"), `To Soft Object Reference`, `Load Asset Blocking`,
  `Cast To InputMappingContext`. The editor redirects `/Game` picks of an overridden asset to the mod copy, and only the
  game-path object carries the player's binds. Loading `/<Mod>/...` soft paths by string returned null.
- **Runtime key sync** (works): load the game-path `IMC_Exploration` and the target context, `UnmapAllKeysFromAction` for
  the actions you carry, `MapKey` each exploration row's key for those actions, then
  `EnhancedInputLibrary.RequestRebuildControlMappingsUsingContext(target, true)`. The player's own keys then work without
  any Options visit.
- **Own context instead of overriding**: add `IMC_<Short>` above the game's context on entry and remove it on exit; a
  higher-priority context shadows the same keys in lower ones without editing them. Remember what YOU added and remove only
  that: re-adding `IMC_Dialog` after the UI removed it leaked the dialogue keys (Q/E/L, pad X/Y/D-pad) into free play
  until a reload.
- **Context override by moved objects** (headless): duplicate the vanilla context into the mod, duplicate the source context
  (such as `IMC_Exploration`) to a temp asset, and MOVE its rows' modifier, trigger and mappable-settings objects
  (`rename(outer=override)`) into the override. That keeps dead zones, response curves and the game's custom
  `ApplySensitivity` modifier intact; setting properties on fresh objects fails ("cannot be edited on templates"). Never
  save or `delete_asset` the temp (delete crashes the commandlet).
- **Check trigger thresholds when copying or overriding a context.** The vanilla `IMC_PlayerCA` mouse-look row
  (`IA_LookUp` / `Mouse2D`, `InputTriggerDown`) has actuation threshold 0.5, `IMC_Exploration`'s has 0.0: while that
  context handled the mouse, small slow movements were silently dropped ("laggy camera"). Measure with
  `PlayerController.GetInputMouseDelta` against the change of `ControlRotation`, not by feel.
- Two rows with the same key in one context fire both actions.
- Input from a mod actor: `EnableInput` + EnhancedInputAction events; the events arrive through the game's own
  `PlayerEnhancedInputComponent`. Upstream's input notes warn that binding an action the game's delayable handlers also
  bind can crash (`IA_PlayerCAExit`); its later game notes say binding `IA_PlayerCAExit` (Started) in a mod actor is fine
  and that the crashes once blamed on it were post-process anim swaps (stalker2-animation). Caution: this point is open; test it before relying on either statement.

## Widgets from Python
- Python cannot edit a Widget Blueprint's tree (`WidgetTree` is protected; `WidgetBlueprintFactory.RootWidgetClass` is
  protected, so a Python-made Widget Blueprint has no root), and Blueprint cannot `Construct Object` a UWidget
  (`DontUseGenericSpawnObject`).
- Build the tree from transient widgets in editor Python (`unreal.new_object`, `add_child_to_vertical_box`,
  `add_child_to_canvas`, set properties), export each with an `AssetExportTask` + `unreal.ObjectExporterT3D()`, strip
  `ExportPath=` and concatenate: that is the Widget Designer's clipboard format. The user pastes it into the empty
  Hierarchy (the first block, such as a Canvas Panel, becomes the root).
- Add `bIsVariable=True` to widgets another Blueprint reads (TextBlocks default to false, Sliders to true); read them with
  a variable get whose MemberParent is the widget class.
- `UUserWidget::GetWidgetFromName` is not Blueprint-callable in 5.5, and native widget members bound with BindWidget are
  usually not Blueprint-visible either. Find a child widget with `GetAllWidgetsOfClass(<its class>, TopLevelOnly=false)` +
  `GetPathName` contains `<Parent>.WidgetTree.<Child>` (once, on an edge).
- `PC` is the player CHARACTER: `IsInputKeyDown`, `CreateWidget`'s Owning Player, input modes and `bShowMouseCursor` need
  `GetPlayerController(0)` (PlayerController), not a `PC` reference.
