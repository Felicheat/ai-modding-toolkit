# STALKER 2 game updates

An "update check" means: did GSC change the game, and does each mod still hold on the new build.

## 1. Did the game update?
- `python scripts/game_build.py` reads the Steam manifest (`appmanifest_1643320.acf`): build id, `LastUpdated`,
  `StateFlags` (4 = fully installed, anything else = update pending or running) and compares the build with the one
  this pack was verified on (26123434) and with your last `--record`. It also shows Steam's last logged update
  (`<Steam>/logs/content_log.txt`: `update started`, `finished update ... (BuildID N)`, files updated). Exit 1 means
  a new build or an update in progress.
- A launch that does nothing while Steam is downloading is an update installing first, not a mod crash. Wait for
  StateFlags 4.
- Steam can push a new build with no new version number. The exe's FileVersion is always `UE5-CL-0`: useless.
- Not a Steam install: no manifest; compare content directly (section 3).

## 2. Keep baselines BEFORE the next update
- A baseline is a folder of the vanilla files a mod replaces or patches, laid out by their path in the game.
  - Cfg tables: `python scripts/compare_tables.py <baseline> --extract <list>` (a file of entries, or `a,b,c`;
    full entry paths or table names).
  - Cooked assets: `python scripts/compare_tables.py <baseline> --cooked <fragment> --save`.
- Keep one baseline per mod project, named by build (`baselines/26123434/`). Without one, a GSC change to a file you
  fully replace goes unnoticed: your copy always wins, so the game never shows the difference.

## 3. After an update: check per mod type
| Mod type | What to check |
|---|---|
| Cfg `{bpatch}` patches | Byte-compare each patched table. If changed, decode and diff (stalker2-cfg) and confirm every patched record still exists with the vanilla value you assumed. |
| Cfg whole-file replacements | Byte-compare each replaced table. Any change: rebuild on the new vanilla, or the mod silently reverts GSC's change. |
| Cooked assets (curves, data tables) | `compare_tables.py <baseline> --cooked <fragment>`. No baseline: extract the new vanilla copy and compare it with your patched legacy copy; same size with only your patched bytes different means unchanged. |
| Zone Kit full replacements (materials, Niagara) | As cooked assets. Your copy always wins, so only the baseline shows a GSC fix. |
| Engine.ini cvars, post-process, LUTs | The exe changed in most updates: check in game; cvars can be renamed or ignored. |

- `python scripts/compare_tables.py <baseline>` compares every cfg file in the baseline with the game's paks (base,
  Cost of Hope, editions) and prints IDENTICAL / CHANGED / MISSING with sha256.
- Compare content, never file dates: Steam re-stages whole containers, so new dates on unchanged data are normal.
- The Zone Kit lags the game version (and may re-date files without new data): its text tables are not proof of
  the new game's values, and a kit cook carries the kit's copy of every asset it includes.
- **Update the kit and re-cook kit mods.** Cooked properties are unversioned (read by index against the class layout). If GSC
  adds a property to a class, a cook from an older kit puts every later value one slot off: no crash, values just land in the
  wrong settings. Classes GSC did not change re-cook identically, so compare each override with GSC's new cooked copy.
- Best check of all when a mod is generated by a build script: rerun it against freshly extracted vanilla into a
  scratch folder and diff its output with what ships.

## 4. Report, rebuild, prove, record
1. Report per mod: **identical**, **changed** (which files, what changed) or **not checked** (name the files and
   why). Never call a mod compatible on files you did not check.
2. Rebuild only mods whose inputs changed; ship them through stalker2-release.
3. Prove the result in game with one loud check per changed area and a control (stalker2-testing).
4. Record the checked build: `python scripts/game_build.py --record --note "<what was checked>"`.

Read references/build-history.md for what the last checked updates changed, the byte-identical lists and a model
checklist of tables to compare.

## Traps
- Cost of Hope cfg is in its own pak (`<game>/DLC1/S2_DLC1Stalker2-Windows.pak`), and its cooked assets sit in the
  DLC1 container that `to-legacy` over `<paks>` cannot see (stalker2-paks).
- `--cooked` fragments are case-sensitive substrings of the `Stalker2/Content/...` file path; a wrong one matches
  nothing (the script stops with exit 2).
- A baseline made from the kit's text tree is not a game baseline: extract from the game's paks.
