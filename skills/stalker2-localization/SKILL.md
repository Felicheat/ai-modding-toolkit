# STALKER 2 localization: a mod's own text

How the game stores localized text and how a mod adds or changes it, from the game's `.locres` files, the Zone Kit's
text assets and in-game tests. This skill owns adding and shipping text. Looking up an in-game name or a key in the
game's `Game.locres` belongs to stalker2-gamedata (its `locres_lookup.py` reads and searches the file). Voiced lines
and TextTool characters: stalker2-voiceover.
Adapted from the Stalker 2 modding harness (github.com/noahsemus/stalker2-modding-harness, MIT, copyright Noah Semus); this part was contributed there by sdwvit.

## Where vanilla text lives
- One `Game.locres` per culture, loose inside the plain `.pak` (not the `.utoc`) of `<paks>/pakchunk0-Windows.pak`,
  at `Stalker2/Content/Localization/Game/<culture>/Game.locres`. Any tool that reads plain paks reaches it
  (`repak get <pak> <path>`, `UnrealPak <pak> -Extract <dir>`). The format is `.locres` v3
  (`Optimized_CityHash64_UTF16`).
- 18 cultures, in `ELocalizationLanguage` order: `en uk de fr es it pl cs tr sr pt-BR es-419 ar zh-Hans zh-Hant ja ko
  ru`. Ukrainian is `uk`. `es` = SpanishEuropean, `es-419` = SpanishLatinoAmerican, `pt-BR` = PortugalBrazilian.
- About 82.9k keys per culture, all in one namespace, `ST_S2BaseGameLocalization`. Only about 49.6k have English
  text; the rest ship an empty string (placeholders, cut content).
- Redo any dump after each game patch: official wording changes.
- The kit's `Stalker2/Content/TextToolBackup/TextDatabase.json` was a 0-byte stub in the kit checked; it is not a
  text source.

## Key names (SIDs)
| Prefix | Text |
|---|---|
| `sid_character_<NPC prototype id>` | NPC names (`sid_character_micman_0` is "Ensign") |
| `sid_topic_<DialogChainSID>` | topic line in the NPC's dialog menu |
| `sid_label_<label>` | short reply option (the player's choice) |
| `sid_phrase_<TextToolPhraseSID>` | a full spoken line |
| `sid_notes_` | notes / documents |
| `sid_items_<ItemSID>_name` / `_description` / `_short_name` | item text; `_short_name` only on weapons and ammo (tight UI slots) |
| `sid_journal_<QuestSID>_Name` | journal quest title |
| `sid_journal_description_<DescriptionSID>` | journal description |
| `sid_journal_stage_<StageSID>` | journal stage (keyed by the stage SID, not its `Description` field) |

- **Items:** name and description are not prototype fields; the game derives `sid_items_<SID>_name` /
  `_description` from the item prototype's `SID`. A new item needs only that pair; without it the UI shows the raw
  SID. The prototype field `LocalizationSID` redirects the lookup to `sid_items_<LocalizationSID>_name` (vanilla
  mutant loot `mutpartspack_*` does this), so variants can share one text.
- **Dialog phrases:** a `DialogPrototype` with no `TextToolPhraseSID` has no text key. Vanilla copies
  (`..._41275_1`) reuse the original's `TextToolPhraseSID`.
- **Labels are derived:** the game drops the last `_<segment>` of a `TextToolPhraseSID` to find the reply label
  (`RSQ01_Dialog_Warlock_RSQ_confirm_26957` gives `sid_label_RSQ01_Dialog_Warlock_RSQ_confirm`; that text is the
  answer option in WaitForReply pickers). So name every phrase `<label SID>_<NNN>` (vanilla: `<label>_<5-digit id>`).
  The cut is always at the last `_`: `Foo_Accept_Bar_1` was read in game as `sid_phrase_Foo_Accept_Bar`, and
  `Foo_Accept_Accepted_1`'s label as `sid_label_Foo_Accept`.

## How a mod ships text
1. In the Zone Kit, the Text Tool creates the text assets in the mod's `Content`: a `LocalizationModTextToolAsset`
   (free-form SIDs, each with a string per language) and, for dialogs, a `DialogModTextToolAsset`.
2. At cook the editor gathers every text asset into ONE generated package,
   `Autogenerated_<n>_LocalizationDatabase`, in the mod's `Content`. That database is what the game reads. `<n>` is
   the save's Unix timestamp; once cooked, that name is the mod's identity.
3. The `.uplugin` lists no assets: anything in `Content` gets cooked. Cooking and packing: stalker2-zonekit.

Read references/text-assets.md before creating or editing a text asset by hand or by script, when a dialog's topic,
label or phrase SIDs must line up, when the cook log's localization lines need reading, and for the language enum
names.

## Overriding vanilla text
- A mod's localization database **overrides** base-game keys (verified in game: 22 vanilla `sid_label_*` dialog
  options re-worded with no cfg patch). Renaming any shipped string is a text-only mod.
- Supply every language for an overridden key; a language left out falls back to English. Take the official wording
  of the other cultures from the game's `.locres` files.

## Checks
- The UI shows a raw key (`sid_items_<SID>_name`): the key is not in the cooked database. Extract the staged
  container and search for the SID before suspecting anything else (it is stored as an FString: a plain byte or
  UTF-16 search of the `.ucas` finds it); then check the database's name (one per mod) and that the key spelling
  matches the derivation rules above.
- A new item shows its SID: the `sid_items_<SID>_name` pair is missing or `LocalizationSID` points elsewhere.
- A reply option shows the wrong text or a raw key: the phrase SID's last `_` segment cut it differently than meant.

## Traps
- A key missing from a dump of one culture often exists but is blank: check another culture before concluding that
  a key does not exist.
- Search dumps case-insensitively: both halves of a name can be present while the exact casing typed is not.
- **One database per mod.** A second `Autogenerated_<m>_LocalizationDatabase` with the same SIDs left in `Content`
  (for example after copying assets between machines) is cooked too, and the two can land in different containers.
  Delete the stale one.
- Copying another mod's text asset and renaming the file leaves its package name pointing at that mod: create a
  fresh asset in the Text Tool. Two mods must not share one `LocalizationId`.
